# 分区检索第一版

新增 RAG_PARTITION_MODE=off/strict/dual。默认 off；不改现有 .env 或远端部署。
查询选择器复用 MultiLabelJudge，以固定选项选择可能提供证据的分区。
不改写问题、不生成答案、不使用基准答案指导路由。

dual 使用一次全库基础召回评分，再独立筛出选中类型候选；半数预算预留给
类型并集，其余由全库填充，重叠候选只保留一次，统一调用重排。
它尚未实现分区 SQL/vector 索引读取优化。预算不足时会挤掉部分原全库候选，
因此不承诺双通道绝无退化。多标签是并集，不给每个标签分别保底。
标签过滤配置仍作用于基础候选；本次真实测试关闭了额外关键词标签过滤。

## 验证

267 项自动测试通过。新测试覆盖候选保底、预算、去重、缺失类型、HTTP
响应兼容、一次查询向量化与一次重排、严格分区、路由失败回退。

真实测试通过 /add 写入 16 条人工英文消息，同一用户同一会话，包含四种类型
及相似主题干扰；通过 /search 执行 8 道单证据问题，每种模式各 8 次。
使用根 .env 的真实写入分类模型、检索路由模型、embedding 和 reranker。
每种模式最终 top_k=5、重排预算上限 8；严格模式候选较少时使用实际数量。

| 模式 | Hit@5 | Recall@5 | 平均查询秒 |
|---|---:|---:|---:|
| 全库基线 off | 100% (8/8) | 100% | 0.232 |
| 仅分区 strict | 87.5% (7/8) | 87.5% | 3.410 |
| 双通道 dual | 100% (8/8) | 100% | 3.640 |

每题仅一个标注目标来源，因此本次 Hit 与 Recall 数值相同。
双通道相对基线没有救回题或新增失败题，平均增加约 3.41 秒，约 15.7 倍延迟。

严格分区失败题：Where does Arun work?
正确原文：Arun works at Riverside School.
写入路由记录的 profile 索引为 [0,1,7,15]，relationship 为 [2]，
event 为 [6,7,12]，rule 为 [4,5,14]，正确原文索引 3 未进入任何类型索引。
它仍保存在原文库，所以全库基线和双通道均将其返回第一名。
这验证了全库补充能补救此例中的写入分类遗漏。

原始响应、耗时和数据库位于 data/partition-live/20261008T113437Z。
脚本：python -m scripts.test_partition_live，每次使用新目录。

## 限制与结论

这不是公开数据集评测。小样本且基线已满分，无法证明普遍质量提升。
strict 与 dual 各自真实调用路由模型，可能存在路由随机性；不能把两者差异
全部归因于候选合并。未逐次保存路由结果的本次结果不用于路由准确率统计。
有必要在更大固定样本上复用同一次路由结果、控制同候选预算后进一步对比。
因此保留 off 为默认，dual 作为已实现且可独立开启的实验。
