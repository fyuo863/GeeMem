# LLM 多跳测试报告（2026-10-03）

## 版本与测试范围

实验分支 `codex/llm-multihop` 从 `main@b90ea62` 创建。实现提交为 `3c59cac`、`f3cb611`；以下真实测试使用 `f3cb611` 的检索实现。测试脚本新增了候选数、top_k 和单题选择参数，各输出目录 manifest 保存实际源码哈希。

实际模型为 gpt-4o-mini、百炼 text-embedding-v4、本机 MiniLM CUDA。配置仅来自项目根 `.env`；测试在进程中开启多跳，使用隔离数据库，没有修改生产配置或部署。接口测试通过 FastAPI TestClient 调用真实 Add/Search 处理器，模型请求真实联网，不是远端服务器压测。

公开回归使用 LongMemEval-S 的 8 道既有开发样本及完整历史（3,926 条消息、5,268 个块）。这些题此前已用于分析，不是独立保留集，也不是官方成绩。另有 4 个自建功能场景及 1 个缩小候选池的链式追查场景。没有生成最终答案，因此指标衡量原文证据召回，不代表答案准确率。

## 自建场景与依赖式追查

默认配置下 4 个自建场景均无回退，策略分别为 direct、split、chain、chain。基线 Recall@3/@5 为 91.67%、Micro Recall 为 87.50%、全证据命中为 75%；LLM 编排均为 100%。双方 @10 各指标均为 100%。平均耗时 0.287 s → 13.643 s。

但是这 4 题均在第一轮检查结束，初始候选包已经包含所需关系，不能用于证明模型成功逐步发现缺失实体。

为检查真正的下一跳，另用 `synthetic-3`，设置 top_k=3、每条子查询候选数=1。问题为：

> Who is the CEO of the company where the spouse of Nadia works?

完整 gold 链为 Nadia → 配偶 Elias → 就职 Solstice Analytics → CEO Ruth Chen。首次候选有配偶与 CEO 原文，但缺少 Elias 的公司。模型正确发现缺口，却输出：

```json
{
  "query": "What company does Elias work for?",
  "source_id": "__question__",
  "bridge": "spouse of Nadia"
}
```

此处 Elias 来自原文 `Nadia is married to Elias.`，并非原问题。所声明的 bridge 又未出现在新查询中。程序按出处约束拒绝该查询，停止于 `no_grounded_new_query`。两种模式 Recall@3 均为 66.67%，全证据命中均为 0%，耗时 0.411 s → 16.007 s。

正确的下一跳应引用配偶原文的实际 ID，并以 `Elias` 为 bridge。当前失败属于模型生成的查询、桥接词与来源 ID 不一致，严格校验将其拦截；不是检索器证明找不到就业原文。引用校验只能验证出处，不能证明逻辑关系成立，例如孤立 CEO 原文在就业关系找到前仍不足以支撑答案。

下一步建议针对校验失败增加一次受预算约束的结构化纠错，把失败原因及可用原文 ID 反馈给模型；不要无条件放宽来源约束。该修复尚未实施，应使用新建的依赖链保留集验证，不继续只调这道样例。
